# Система абитуриента ИМиКН БГУ

Веб-система для абитуриентов Института математики, физики и компьютерных наук
Бурятского государственного университета: каталог мероприятий, запись на них,
анкеты абитуриентов и выставление дополнительных баллов приёмной комиссией.

**Стек:** Python 3.13 · Django 5.2 · PostgreSQL 17 · HTML/CSS без фреймворков.
**Защита:** Argon2id для паролей, TOTP-2FA («Яндекс Ключ»), резервные коды,
лимиты попыток, журнал входов, жёсткие заголовки безопасности.
**Уведомления:** чат-бот в мессенджере MAX (Bot API).

---

## 1. Быстрый старт

```bash
# 1. Зависимости в изолированное окружение
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

# 2. База данных PostgreSQL (один раз, от имени пользователя postgres)
sudo -u postgres psql -c "CREATE ROLE bgu_app LOGIN PASSWORD 'postgres-password'"
sudo -u postgres createdb -O bgu_app bgu_applicants
# CREATEDB нужен для прогонов тестов (создаётся тестовая копия базы)
sudo -u postgres psql -c "ALTER ROLE bgu_app CREATEDB"

# 3. Конфигурация
cp .env.example .env          # заполнить POSTGRES_PASSWORD и DJANGO_SECRET_KEY

# 4. Миграции и демо-данные
python manage.py migrate
python manage.py seed_demo

# 5. Запуск
python manage.py runserver
```

Открыть <http://127.0.0.1:8000/>.

## 2. Роли и сценарии

**Абитуриент** регистрируется сам, заполняет анкету (ФИО, дата рождения,
направление, баллы ЕГЭ), подаёт её комиссии, смотрит каталог опубликованных
мероприятий, записывается и отменяет запись, следит за начисленными баллами.

**Администратор приёмной комиссии** создаёт и правит мероприятия, публикует их
и отменяет, видит список записавшихся, выставляет баллы за участие (0–10),
меняет статус анкеты и комментирует решение.

Разделение ролей сделано на уровне сервера: раздел `/office/` недоступен
абитуриенту (HTTP 403), а личный кабинет абитуриента — администратору.
Роль нельзя повысить со стороны клиента.

## 3. Структура базы данных

Основные таблицы по требованиям задания:

| Таблица | Назначение |
| --- | --- |
| `events_event` | Мероприятия: название, тип, дата, место, вместимость, доп. баллы, статус |
| `accounts_applicantprofile` | Данные абитуриента: ФИО, контакты, направление, баллы ЕГЭ, статус анкеты, доп. баллы |

Служебные таблицы:

| Таблица | Назначение |
| --- | --- |
| `accounts_user` | Учётные записи: email как логин, хеш пароля, роль, привязка MAX |
| `events_enrollment` | Запись абитуриента на мероприятие + выставленные баллы |
| `accounts_totpdevice` | Секрет TOTP, отметка подтверждения, защита от повтора кода |
| `accounts_recoverycode` | Резервные коды (хранится только их хеш) |
| `accounts_onetimecode` | Одноразовые коды, отправляемые в MAX |
| `accounts_loginlog` | Журнал входов: успех, неверный пароль, ошибки 2FA, обход 2FA, выход |
| `django_session` | Сессии в базе (срок 30 минут бездействия) |

Схема: `User 1—1 ApplicantProfile`, `User 1—N Enrollment N—1 Event`
(уникальность пары «мероприятие + абитуриент» закреплена ограничением БД).

## 4. Безопасность

| Механизм | Реализация |
| --- | --- |
| Хеширование паролей | `Argon2PasswordHasher` (Argon2id), PBKDF2 и bcrypt — на случай миграции |
| Сложность пароля | ≥10 символов, запрет полностью числовых, популярных и совпадающих с почтой |
| Второй фактор | TOTP (RFC 6238), 6 цифр, шаг 30 с, допуск ±1 шаг; секрет одноразово показывается в QR и base32 |
| Защита от повтора | Использованный TOTP-шаг запоминается, повтор кода в следующем окне отклоняется |
| Резервные коды | 8 кодов, хранятся как хеши, расходуются однократно, перевыпуск отменяет прежние |
| Обязательность 2FA | `SessionSecurityMiddleware`: аутентифицированная сессия без подтверждённого второго фактора завершается, попытка фиксируется в журнале |
| Перенастройка 2FA | Новый секрет не выдаётся сессии, знающей только пароль: иначе украденный пароль позволил бы привязать свой телефон и обойти второй фактор. Перенастройка доступна после подтверждения входа |
| Обход через `/admin/login/` | Закрыт тем же middleware: вход в админ-панель Django возможен только после 2FA и только для роли администратора |
| Подбор пароля | 10 неудачных попыток на 10 минут → временная блокировка |
| Подбор кода 2FA | 5 неудачных попыток на 5 минут, событие в журнале |
| CSRF, XSS | Токены на всех формах, автоэкранирование шаблонов, `SameSite=Lax` |
| Cookies | `HttpOnly`, `SameSite=Lax`, имя `bgu_sessionid`, срок 30 минут, удаление при закрытии браузера |
| Заголовки | `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`, HSTS при HTTPS, `Cache-Control: no-store` для персональных страниц |
| Перечисление аккаунтов | Неверная почта и неверный пароль дают одно и то же сообщение |
| Ошибки | При `DEBUG=0` — собственные страницы 400/403/404/500 без трейсов и списка маршрутов |
| Спам-боты | Скрытое поле-приманка на регистрации |

### Проверка

```bash
python manage.py test                 # 37 тестов
curl -i http://127.0.0.1:8000/healthz # проверка соединения с PostgreSQL
python manage.py check --deploy       # рекомендации по прод-конфигурации
```

Собственные страницы ошибок работают при `DJANGO_DEBUG=0` (рабочая установка).
При `DJANGO_DEBUG=1` Django показывает отладочную страницу с деталями — это
штатное поведение фреймворка для разработки; в `.env` для демонстрации без
отладки поставьте `DJANGO_DEBUG=0` и запускайте
`python manage.py runserver --insecure`, чтобы раздавать CSS.

## 5. Бот в MAX

Бот отправляет абитуриенту уведомления о начисленных баллах, об изменении и отмене
мероприятия, об изменении статуса анкеты, а также может служить вторым фактором
входа (одноразовый код в чат).

Интеграция использует MAX Bot API (`https://platform-api2.max.ru`), токен
передаётся заголовком `Authorization`:

- `POST /messages?user_id=…` — отправка сообщения в диалог;
- `POST /subscriptions` — регистрация webhook для приёма событий;
- `POST /max/webhook/` — наш эндпоинт, проверяет заголовок `X-Max-Bot-Api-Secret`
  и всегда отвечает `200`, чтобы платформа не отписала бота.

### Подключение

1. Создать бота в MAX (платформа `business.max.ru` → «Чат-боты») и скопировать токен.
2. Указать в `.env`:
   ```
   MAX_BOT_TOKEN=<токен>
   MAX_BOT_USERNAME=<ник бота>
   MAX_WEBHOOK_SECRET=<5-256 символов A-Z a-z 0-9 _ ->
   ```
3. Зарегистрировать webhook (нужен публичный HTTPS на порту 443):
   ```bash
   curl -X POST "https://platform-api2.max.ru/subscriptions" \
     -H "Authorization: <токен>" -H "Content-Type: application/json" \
     -d '{"url":"https://ваш-домен/max/webhook/",
          "update_types":["message_created","bot_started"],
          "secret":"<MAX_WEBHOOK_SECRET>"}'
   ```
4. В личном кабинете абитуриента открыть «MAX-бот» → «Получить код привязки»
   и отправить боту сообщение `LINK XXXXXXXXXXXX`.

Если `MAX_BOT_TOKEN` не задан, интеграция автоматически отключается: интерфейс
сообщает об этом, а остальные функции работают без изменений — это удобно для
демонстрации без доступа в интернет.

## 6. Настройка окружения

| Переменная | Назначение |
| --- | --- |
| `DJANGO_SECRET_KEY` | Ключ подписи; в проде обязательно свой |
| `DJANGO_DEBUG` | `1` — отладка, `0` — рабочая установка |
| `DJANGO_ALLOWED_HOSTS` | Список доменов через запятую |
| `POSTGRES_*` | Параметры подключения к PostgreSQL |
| `DJANGO_COOKIE_SECURE`, `DJANGO_SECURE_SSL_REDIRECT` | Включать при работе по HTTPS |
| `SESSION_COOKIE_AGE` | Срок сессии в секундах (по умолчанию 1800) |
| `MAX_*` | Токен бота, ник, секрет webhook, режим второго фактора |

## 7. Структура кода

```
config/        настройки, маршруты, WSGI/ASGI
accounts/      пользователи, роли, анкета, 2FA, MAX, журнал входов
  services/    totp.py — второй фактор; max_bot.py — клиент MAX Bot API
  security.py  декораторы ролей, лимиты попыток, состояние 2FA в сессии
  middleware.py защита сессий и запрет обхода 2FA
  management/commands/seed_demo.py — демо-данные
events/        мероприятия, записи, выставление баллов, панель комиссии
templates/     HTML-шаблоны (base, accounts, events, errors)
static/css/    стили без внешних зависимостей
```
